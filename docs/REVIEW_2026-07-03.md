## 1. Executive Summary

cc-loop v0.10.0 is a **solid, well-architected CLI orchestrator** with clean module boundaries, thorough test coverage (179 tests), and a disciplined integration contract. The recent v0.5–v0.10 evolution delivered runner reliability, recovery dispatch, parallel execution, and observability artifacts on a tight schedule.

**The core problem:** Prompt cache hit rate is stuck at ~63% despite multiple optimization rounds. The root cause is architectural, not incremental — the current "stable prefix + dynamic payload" pattern puts too much content after the dynamic marker, and provider subprocess isolation prevents cross-phase cache reuse.

**The product direction is unclear.** Four related projects (cc-loop, cc-loop-benchlab, PromptOpsWorkbench, Luma) have overlapping concerns. Without a clear boundary definition, each project will drift and duplicate effort.

**This review provides 40+ concrete, executable recommendations** across cache optimization, workflow redesign, product positioning, benchmark evolution, and Luma integration. Each recommendation includes specific files to modify, acceptance criteria, and whether cc-loop itself can execute the change.

## 3. Cache Hit Rate Diagnosis

### 3.1 The Numbers

**Real user data (Claude Code token usage):**

| Run | Total | Cache Hit | Cache Miss | Output | Hit Rate |
|-----|-------|-----------|------------|--------|----------|
| Run 1 | 2,162,815 | 1,309,824 | 786,753 | 66,238 | 62.5% |
| Run 2 | 2,586,550 | 1,604,992 | 907,926 | 73,632 | 63.9% |

**Benchlab reviewer metrics:**
- `stable_prefix_ratio`: 0.159567 (meaning 84% of reviewer prompt is dynamic)
- `cache_health`: poor
- `total_prompt_cache_health`: poor
- `omitted_patch_chars`: 51,129 (artifact_refs working correctly)
- `estimated_avoidable_miss_tokens`: 12,783

### 3.2 Root Cause: Why Cache Hit Rate Is Only ~63%

**Finding 1: The reviewer prompt's stable prefix is too small relative to the dynamic payload.**

The reviewer prompt structure (from `run.py:2026-2118`):

```
Stable prefix (~1500 chars):
  "You are the cc-loop reviewer."
  Stable Review Contract (7 rules)
  Stable Review Rubric (7 rules)
  Stable JSON Output Contract (JSON schema)
  "## Dynamic Review Payload"

Dynamic payload (~8000+ chars, 84% of total):
  Attempt metadata (task ID, goal, iteration, retry, graph node, exit codes, commits)
  Node section (node ID, title, kind, description, acceptance criteria, dependencies)
  Review context (mode, inline_patch, ALL artifact paths, selected patches, omitted chars)
  Test result section
  ### Diff stat (git diff --stat output — ALWAYS inlined!)
  ### Selected patches OR Patch artifact references
```

The `stable_prefix_ratio` of 0.16 means **for every 1000 tokens in the reviewer prompt, only 160 are cacheable.** The remaining 840 tokens change on every attempt and always miss the cache.

**Finding 2: `git diff --stat` is ALWAYS inlined, even in `artifact_refs` mode.**

Look at `build_reviewer_prompt()` line 2102-2104:
```python
"### Diff stat\n"
f"{diff_stat}\n\n"
```

The `diff_stat` is placed AFTER the `## Dynamic Review Payload` marker in EVERY reviewer prompt, regardless of `context_mode`. For a multi-file change, `git diff --stat` can be hundreds of lines. This is a **major cache miss contributor** that `artifact_refs` does not address.

**Finding 3: The attempt metadata section varies on every call.**

Task ID, goal, iteration, retry, base/head commit, graph node — these ALL change between attempts. Even within the same task, iteration and retry increment. The graph node changes as we move through the task graph.

**Finding 4: Provider subprocess architecture prevents cross-phase cache reuse.**

Each phase (planner, implementer, reviewer) spawns a **fresh subprocess** for the provider CLI. Claude's prompt cache is per-API-request within a session. When cc-loop calls `claude -p "..."` three separate times, each call starts with a cold cache.

The Anthropic prompt cache can cache prefixes across requests within the same conversation, but cc-loop doesn't maintain a conversation — it sends isolated one-shot prompts.

**Finding 5: The implementer prompt has negligible cache benefit.**

`_IMPLEMENTER_STABLE_CONTRACT` is only 6 lines (plus header):
```
You are the cc-loop implementer.
## Implementer Contract
- Keep changes scoped...
- Do not perform unrelated refactors...
- Do not undo user changes...
- Add or update tests...
- Do not weaken existing tests...
- Preserve existing code patterns...
## Dynamic Implementer Payload
```

After this tiny prefix, the dynamic payload includes: task ID, goal, iteration, implementation prompt (from planner), expected changes, acceptance criteria. For graph node-scoped prompts, even more dynamic content: graph summary, node description, node kind, files scope, completed dependencies, node instructions.

The implementer prompt is **almost entirely dynamic** — the stable prefix is negligible.

### 3.3 Phase-by-Phase Cache Impact Analysis

| Phase | Cache Reuse Potential | Current State | Optimization Opportunity |
|-------|----------------------|---------------|--------------------------|
| **Planner** | Low (called once per task usually) | `planner_mode=direct` skips entirely | When not skipped, cache matters for replanning |
| **Implementer** | Medium (same task context, new prompt per node) | Stable prefix is ~6 lines | Can be cached with session reuse + task payload file |
| **Reviewer** | **HIGH** (same rubric, same contract, different patch) | 16% stable prefix ratio | Two-stage review + diff stat artifact ref + fragment files |

### 3.4 Why Direct Planner Mode Isn't Being Used Aggressively Enough

`planner_mode=direct` is available but the default is `auto`. The `planner_granularity.py` heuristics try to detect when `single` is appropriate, but `direct` is only used when explicitly requested.

**Problem:** The `--planner-mode direct` flag exists, but:
1. No automatic fallback to `direct` when the goal is simple
2. No heuristic that detects "this is a single-file fix, skip the planner"
3. Benchlab scenarios use `direct` for `small_cli_fix` and `docs_only_change` but `single` for others — the pattern should be inverted (direct should be the default for small tasks)

**Recommendation:** Make `direct` the default for goals under a complexity threshold. See Section 7.

### 3.5 The "Three Buckets" Model of Cache Miss

Every reviewer prompt can be decomposed into three buckets:

| Bucket | Content | Cache Behavior | % of Prompt |
|--------|---------|---------------|-------------|
| **Stable Contract** | Review rubric, JSON schema, rules | Always cached (if prefix) | ~16% |
| **Task Context** | Goal, node criteria, file scope | Changes per task but NOT per attempt | ~20% |
| **Evidence** | Diff stat, patches, test results | Changes on EVERY attempt | ~64% |

The current design puts Bucket 2 (Task Context) and Bucket 3 (Evidence) together after the dynamic marker, destroying cacheability for Bucket 2.

## 4. Workflow Diagnosis

### 4.1 Current Pipeline Assessment

```
planner → implementer → tests → reviewer → merge
```

**Strengths:**
- Clear phase separation
- Each phase has independent timeout, provider, and error handling
- Recovery dispatch is centralized and well-tested
- Task graph supports multi-node sequential/parallel execution

**Weaknesses:**

**4.1.1 Small tasks waste tokens on planner.**

For a single-file argparse fix, the planner provider is invoked, consumes tokens, and produces a single-node graph. `planner_mode=direct` solves this but requires explicit opt-in.

**4.1.2 Graph planner has no cost/benefit heuristic.**

`planner_mode=graph` always delegates to the planner provider, which may produce an over-decomposed graph (e.g., 5 nodes for a 3-file change). There's no "complexity budget" that limits graph decomposition depth.

**4.1.3 Reviewer is one-size-fits-all.**

Every review goes through the same `build_reviewer_prompt()` path. There's no:
- **Fast review** (artifact refs only, approve if tests pass + diff is small)
- **Deep review** (inline patches, full analysis, triggered by risk signals)
- **Risk-triggered review** (large diff, security-sensitive files, first-time contributor)

**4.1.4 Recovery is good but has gaps.**

`patch_not_captured` recovery runs the implementer again with a targeted prompt. But:
- If the implementer produces 0-byte output (common with Cursor), recovery waits for timeout
- If tests fail due to environment issues (missing dependency), recovery retries implementation instead of fixing the environment
- `provider_timeout` recovery doesn't distinguish between "model is thinking" and "model is hung"

**4.1.5 Cursor implementer observability is poor.**

When Cursor produces 0-byte `implementer.raw.json` for extended periods:
- No intermediate progress signal (is it thinking? hung? downloading?)
- Heartbeat shows `running_provider: cursor` but no sub-progress
- `command.argv.json` exists but `subprocess.result.json` only appears after completion

**4.1.6 Status/heartbeat synchronization issues.**

`_resolve_live_attempt_fields()` in `inspect.py` merges state.json phase with heartbeat data. If the heartbeat is stale (120s default), the status shows outdated phase information. There's a race between heartbeat refresh and status polling.

### 4.2 Test Failure Recovery Classification

Current recovery dispatch (`recovery.py:decide_auto_step()`):

| Failure | Disposition | Recovery Action | Quality |
|---------|------------|-----------------|---------|
| `merge_conflict` | recoverable | implementer repair | Good |
| `test_implementation` | recoverable | implementer repair with test output | Good |
| `provider_timeout` | recoverable | retry | Adequate — no timeout reason analysis |
| `reviewer_stop_fixable` | recoverable | implementer repair with review feedback | Good |
| `reviewer_stop_terminal` | terminal | stop | Correct |
| `patch_not_captured` | recoverable | implementer repair with porcelain status | Adequate |
| `provider_exit_error` | recoverable | retry | Weak — no error classification |
| `recovery_budget_exhausted` | terminal | stop | Correct |

### 4.3 Missing Observability Signals

| Signal | Current State | Needed For |
|--------|--------------|------------|
| Agent execution timeline | Not implemented | Luma UI, debugging, SLA tracking |
| Phase-level duration percentiles | Not implemented | Provider comparison, cost optimization |
| Task-level SLA/budget | Config exists but not surfaced | User confidence, auto-stop |
| Provider token usage per phase | Heuristic (`chars/4`) only | Real cost tracking |
| Intermediate implementer progress | Not available | Cursor long-running task visibility |
| Run-level summary artifact | Not implemented | Luma run detail view |

## 5. Product Positioning

### 5.1 What Should cc-loop Be?

**Recommendation: cc-loop should be positioned as a "Coding Agent Workflow Runtime" — a local execution engine that orchestrates multi-agent coding pipelines.**

This is distinct from:

| Category | Examples | cc-loop relationship |
|----------|---------|---------------------|
| CLI tool | `gh`, `git` | cc-loop IS a CLI, but that's its interface, not its identity |
| Agent framework | LangChain, CrewAI | cc-loop is higher-level — it orchestrates EXISTING agent CLIs |
| CI/CD | GitHub Actions, Jenkins | cc-loop is local-first, not server-based |
| Prompt manager | PromptFoo, Langfuse | PromptOpsWorkbench handles this |
| Desktop launcher | Raycast, Spotlight | Luma handles this |

**cc-loop's unique value proposition:**
1. It orchestrates REAL agent CLIs (Claude Code, Codex, Cursor) — not SDK abstractions
2. It works with real git repos in isolated worktrees
3. It has production-grade recovery, safety, and observability
4. It's local-first, zero-dependency, zero-network

**Positioning statement:**
> cc-loop is the runtime that turns "fix this bug" into a completed, tested, reviewed, and merged pull request — orchestrating Claude Code, Codex, and Cursor through a recoverable pipeline with full observability.

### 5.2 Three Horizons

| Horizon | Timeline | Focus |
|---------|----------|-------|
| **H1: Solidify** | Now–2 weeks | Fix cache miss, improve observability, stabilize Luma integration |
| **H2: Expand** | 2 weeks–1 month | Two-stage review, session reuse, benchmark CI, SLA/budgets |
| **H3: Platform** | 1 month+ | Shared artifact schema, prompt registry, plugin provider system |

### 5.3 What cc-loop Should NOT Become

- **Not a web service** — stay CLI-first, thin JSON API
- **Not a prompt editor** — that's PromptOpsWorkbench
- **Not a desktop app** — that's Luma
- **Not a model router** — providers are pluggable but cc-loop doesn't choose models
- **Not an enterprise platform** — no RBAC, no multi-tenancy, no cloud coordination

### 6.3 What Should Be Merged

**Option A: Extract `cc-loop-artifacts` shared library (Recommended)**

Create a new package `cc-loop-artifacts` (or `ccloop_artifacts`) that provides:
- `ArtifactSchema` — unified dataclasses for ALL artifact JSON files
- `parse_prompt_cache()` / `parse_review_metrics()` / `parse_attempt_trace()` etc.
- `PromptCacheModels`, `ReviewMetricsModels`, `SubprocessResultModels` etc.

This library becomes a dependency of:
- cc-loop (emits artifacts that conform to schema)
- cc-loop-benchlab (parses artifacts for benchmark reports)
- PromptOpsWorkbench (parses artifacts for import/analysis/report)

**Option B: Merge PromptOpsWorkbench into cc-loop as a subcommand (Not Recommended)**

PromptOpsWorkbench serves a different purpose (prompt management, not agent orchestration). Merging would bloat cc-loop. Keep separate but share the artifact schema library.

Luma should consume these cc-loop outputs:
1. `status --json` (already implemented)
2. `list --json` (already implemented)
3. `report --json` (already implemented, needs `observability` enrichment)
4. `graph --json` (already implemented)
5. **NEW: `cc-loop summary --task-id ID --json`** — a Luma-optimized single-JSON-file summary

The `summary` command should produce a single JSON file that Luma can read without parsing 26 individual artifact files. This is currently what `PromptOpsWorkbench ccloop-summary` provides, but it should be a cc-loop native command.

## 7. Technical Roadmap

### 7.1 P0: Immediate Fixes (This Week)

#### P0-1: Move diff stat to artifact reference in reviewer prompt

**Problem:** `git diff --stat` is always inlined in reviewer prompt, even in `artifact_refs` mode. For a 20-file change, this is ~1000+ chars of dynamic content that ALWAYS misses cache.

**Fix:** In `build_reviewer_prompt()`, when `context_mode == "artifact_refs"` or (`context_mode == "hybrid"` and `not inline_patch`), replace the inlined diff stat with a path reference:
```python
if context_mode == "artifact_refs" or not inline_patch:
    stable_prefix += (
        "### Diff stat\n"
        f"See: {diff_stat_path}\n\n"
    )
else:
    stable_prefix += (
        "### Diff stat\n"
        f"{diff_stat}\n\n"
    )
```

**Files:** `src/cc_loop/run.py` lines 2102-2104  
**Impact:** Reduces reviewer prompt dynamic payload by `len(diff_stat)` chars per review  
**Risk:** Reviewer may not read the referenced file — mitigate with explicit instruction in stable contract  
**Acceptance:** `review.prompt.metrics.json` shows increased `stable_prefix_ratio`  
**Suitable for cc-loop:** Yes, with reviewer=codex, implementer=cursor  

#### P0-2: Increase planner `direct` mode usage with automatic heuristic

**Problem:** `planner_mode=direct` requires explicit opt-in. Most small tasks go through the planner unnecessarily.

**Fix:** Add a `_should_use_direct_planner(state)` heuristic in `run.py`:
```python
def _should_use_direct_planner(state: TaskState) -> bool:
    """Return True when the goal is simple enough to skip the planner provider."""
    goal_lower = state.goal.lower()
    # Single-file fix indicators
    simple_patterns = [
        "fix typo", "fix bug in", "add docstring", "update readme",
        "add comment", "rename variable", "fix import",
    ]
    if any(p in goal_lower for p in simple_patterns):
        return True
    # Short goal with no decomposition keywords
    if len(state.goal) < 200 and not any(kw in goal_lower for kw in ["and", "also", "additionally", "multiple", "several"]):
        return True
    return False
```

Use it when `planner_mode == "auto"` (the default).

**Files:** `src/cc_loop/run.py` (add heuristic), `src/cc_loop/cli.py` (no change needed if auto)  
**Impact:** Skips ~30-50% of planner calls for simple tasks. Saves 500-2000 tokens per skipped planner call.  
**Risk:** False positive — direct mode might be used for tasks that benefit from decomposition. Mitigate with a `--no-direct` flag or `--planner-mode single` override.  
**Acceptance:** Benchlab `small_cli_fix` scenario shows `planner: skipped` in prompt.cache.json even without explicit `--planner-mode direct`.  
**Suitable for cc-loop:** Yes, planner=codex, implementer=cursor, reviewer=codex  

#### P0-3: Fix reviewer `contract_prefix_ratio` — reorder prompt sections

**Problem:** The "Stable Review Rubric" and "Stable JSON Output Contract" are correctly placed before the dynamic marker, but the "Stable Review Contract" content is too long relative to the dynamic payload. The key issue is that task context (goal, node info) is mixed with evidence (diff, patches).

**Fix:** Implement a **two-section dynamic payload**:
1. **Semi-stable context** (changes per task, NOT per attempt): goal, node description, acceptance criteria, files scope
2. **Per-attempt evidence** (changes every attempt): iteration, retry, commits, test status, diff stat ref, patch refs

Place section 1 BEFORE the dynamic marker (making it part of the cacheable prefix) and section 2 after.

New structure:
```
## Stable Review Contract
[unchanged rubric + JSON schema]

## Task Context (stable per task)
Goal: ...
Node: T1 — Fix argparse bug
Acceptance criteria: ...
Files scope: greet.py

## Dynamic Review Payload
Everything below changes per attempt.
### Attempt metadata
Iteration: 2, Retry: 1, ...
### Review context
[paths, refs]
### Test result
[status, output path]
### Diff stat ref
See: diff.stat.txt
### Patch artifact references
[file paths]
```

**Files:** `src/cc_loop/run.py` `build_reviewer_prompt()` (restructure), `build_reviewer_prompt_metrics()` (update marker logic)  
**Impact:** `contract_prefix_ratio` should increase from ~0.16 to ~0.35-0.45 (adding task context to prefix)  
**Risk:** Task context changes on replanning. On replan, the prefix changes, but replanning is rare.  
**Acceptance:** Benchlab reviewer metrics show `cache_health: warning` or `good` instead of `poor`.  
**Suitable for cc-loop:** Yes  

#### P0-4: Add `cc-loop summary --json` command (Luma contract)

**Problem:** Luma currently needs to parse `status --json` + individual artifacts to show task details. PromptOpsWorkbench has `ccloop-summary` but Luma shouldn't depend on PromptOpsWorkbench.

**Fix:** Add a `cc-loop summary --task-id ID --json` command that emits a single JSON file with:
- Task identity (from state.json)
- Current status (from status --json)
- Latest attempt summary (phase, decision, test status, review decision)
- Prompt cache summary (from prompt.cache.json)
- Reviewer metrics summary (from review.prompt.metrics.json)
- Failure summary (from failure.report.json)
- Subprocess results per phase
- Provider command argv (redacted)
- Event counts
- Artifact directory paths

This is essentially what `report --json` already provides, but restructured for Luma consumption with additional fields.

**Files:** New `src/cc_loop/summary.py`, add CLI subcommand in `cli.py`  
**Impact:** Luma gets a single JSON endpoint. PromptOpsWorkbench `ccloop-summary` becomes redundant.  
**Risk:** Schema evolution — document as additive-only.  
**Acceptance:** `cc-loop summary --task-id ID --json` returns valid JSON with all required fields.  
**Suitable for cc-loop:** Yes, with planner=codex, implementer=cursor, reviewer=codex  

#### P0-5: Add `run.summary.json` artifact (per-run summary)

**Problem:** After a task completes, consumers need to parse multiple files to understand what happened. There's no single "run summary" artifact.

**Fix:** Write `<task-dir>/run.summary.json` on task completion (done/failed/stopped/cancelled) containing:
- Task identity, goal, repo
- Total wall-clock time
- Iterations completed
- Nodes completed / failed / skipped
- Final status, decision
- Aggregate token estimates
- Cache health summary
- Provider summary (which providers were used, how many calls)
- Event timeline (key timestamps)
- All artifact directory paths

**Files:** `src/cc_loop/run.py` (`_run_finalize_phase()`), new `src/cc_loop/summary.py`  
**Impact:** Single-file run recap for Luma, PromptOpsWorkbench, and human inspection  
**Acceptance:** After `cc-loop auto --task-id X` completes, `<task-dir>/run.summary.json` exists and is valid.  
**Suitable for cc-loop:** Yes  

#### P0-6: Add agent execution timeline artifact

**Problem:** No time-series view of what happened when. Hard to debug "why did this take so long?"

**Fix:** Add `execution.timeline.json` per task — an array of timed events:
```json
[
  {"timestamp": "2026-07-03T10:00:00Z", "phase": "planning", "event": "started", "provider": "codex"},
  {"timestamp": "2026-07-03T10:00:15Z", "phase": "planning", "event": "completed", "duration_ms": 15234},
  ...
]
```

Build this from `events.jsonl` timestamps + `subprocess.result.json` durations + `attempt.trace.json` phase statuses.

**Files:** `src/cc_loop/events.py` (enrich with duration data), new logic in `run.py` finalize, expose in `summary --json`  
**Impact:** Luma can render a timeline view. Debugging becomes easier.  
**Acceptance:** Timeline JSON has entries for every phase with start/end timestamps.  
**Suitable for cc-loop:** Yes  

#### P0-7: Cursor implementer intermediate progress detection

**Problem:** Cursor can produce 0-byte `implementer.raw.json` for minutes. No way to know if it's working.

### 7.2 P1: 1–2 Week Improvements

#### P1-1: Two-stage reviewer architecture

**Concept:**
```
Stage 1: Fast Review (artifact refs, high cache hit)
  ├─ Inline: nothing (all artifact refs)
  ├─ Checks: tests passed? diff stat looks reasonable? file list matches scope?
  ├─ Decision: approve | escalate
  └─ Cache: stable prefix ~60%+

Stage 2: Deep Review (inline patches, triggered by escalation)
  ├─ Inline: selected patches (bounded)
  ├─ Checks: code correctness, security, style, acceptance criteria
  ├─ Decision: approve | reject | stop | replan
  └─ Cache: lower but only invoked when necessary
```

**Implementation:**
- Add `review_depth` config: `fast` (stage 1 only), `deep` (stage 2 only), `auto` (fast → escalate to deep)
- Stage 1 uses `context_mode=artifact_refs`, checks only test status + diff stat + file list
- Stage 1 prompt is SHORT (~500 chars stable + ~200 chars dynamic)
- Stage 1 gets ~80%+ cache hit rate
- Escalation triggers: tests failed, >10 files changed, security-sensitive paths, diff stat > threshold
- Stage 2 is current reviewer prompt with inline patches

**Files:** `src/cc_loop/run.py` (new `_run_fast_review()` function), `src/cc_loop/config.py` (new config keys)  
**Impact:** 70-80% of reviews complete at stage 1 with high cache hit. Only complex changes incur deep review cost.  
**Risk:** Stage 1 false approval — mitigate with conservative escalation triggers and explicit "fast review limitations" in prompt.  
**Acceptance:** Benchlab shows `fast` review for `small_cli_fix`, `deep` review for `large_patch_review`.  

#### P1-2: Prompt fragment file architecture

**Problem:** All prompts are built as inline Python strings in `run.py`. This makes prompt iteration slow, prevents A/B testing of prompt variations, and couples prompt content to orchestration code.

**Fix:** Create a `prompts/` directory in the cc-loop package with fragment files:

```
src/cc_loop/prompts/
  _init_.py           # Fragment loader, cache
  planner/
    stable_prefix.txt
    task_graph_schema.txt
    legacy_schema.txt
    graph_rules.txt
  implementer/
    stable_contract.txt
    node_scoped.txt
  reviewer/
    stable_contract.txt
    review_rubric.txt
    json_output_contract.txt
    fast_review.txt
    deep_review.txt
```

Each `.txt` file is a plain text fragment. `run.py` loads and composes them. Fragment files can be overridden per-project via a `--prompts-dir` flag.

**Files:** New directory `src/cc_loop/prompts/`, modify `run.py` prompt builders to use fragment loader  
**Impact:** Prompt iteration becomes a text file edit, not a code change. Enables A/B testing via benchlab.  
**Risk:** Fragment loading adds I/O — cache in memory.  
**Acceptance:** Existing tests pass with fragment-based prompts producing identical output.  

#### P1-3: Task context payload file

**Problem:** The same task context (goal, node description, acceptance criteria) is injected into multiple prompts (implementer + reviewer). Each injection is a cache miss.

**Fix:** Write `<attempt-artifacts>/task.context.json` once per iteration containing:
```json
{
  "task_id": "...",
  "goal": "...",
  "graph_node": {"id": "T1", "title": "...", "description": "...", "acceptance_criteria": [...], "files_scope": [...]},
  "completed_dependencies": [...]
}
```

Then in prompts, reference `See: <artifact_dir>/task.context.json` instead of inlining. Providers that can read files (Claude Code, Codex) can access this. For providers that can't, fall back to inlining.

**Files:** `src/cc_loop/run.py`, new logic to write task context artifact  
**Impact:** Reviewer and implementer prompts become shorter. Task context becomes cacheable (same file path, same content for all attempts within an iteration).  
**Risk:** Relies on provider file-reading capability — need fallback.  

#### P1-4: Benchlab A/B variant support

**Problem:** Benchlab scenarios have a single `default` variant. No way to compare `review_context_mode=inline` vs `artifact_refs` or `planner_mode=single` vs `direct`.

**Fix:** Add multi-variant scenarios:
```yaml
name: reviewer_context_ab
variants:
  - name: inline
    commands:
      - ["init", ..., "--review-context-mode", "inline"]
      - ["auto", ...]
  - name: artifact_refs
    commands:
      - ["init", ..., "--review-context-mode", "artifact_refs"]
      - ["auto", ...]
```

Enhance `report.py` comparison table to show per-dimension delta and percentage change.

**Files:** `/Users/diaoyuxuan/cc-loop-benchlab/src/cc_loop_benchlab/report.py`, new A/B scenarios  
**Acceptance:** Running `large_patch_review_ab` produces a report comparing inline vs artifact_refs token usage.  

#### P1-5: Repeated runs with statistical summary

**Problem:** Single-run benchmarks are noisy. Provider LLMs have inherent variance.

**Fix:** Add `repetitions: N` to scenario YAML. Runner executes each variant N times. Report includes:
- Mean, median, stddev for numeric metrics
- Min/max for token usage
- Pass rate for boolean metrics (test status, review decision)

**Files:** `scenario.py`, `runner.py`, `report.py` in benchlab  
**Acceptance:** `repetitions: 3` produces 3 runs per variant with statistical summary.  

#### P1-6: Cost model with real pricing

**Problem:** Benchlab reports show token counts but no dollar cost. Users can't compare provider costs.

**Fix:** Add `cost_model` to benchlab config (JSON file mapping model IDs to input/output token prices):
```json
{
  "claude-opus-4-8": {"input_per_1k": 0.015, "output_per_1k": 0.075},
  "claude-sonnet-4-6": {"input_per_1k": 0.003, "output_per_1k": 0.015}
}
```

Report shows estimated USD cost per variant.

**Files:** New `cost_model.py` in benchlab, `report.py`  
**Acceptance:** Report includes `estimated_cost_usd` per variant.  

#### P1-7: Reviewer false approve/false reject detection in benchlab

**Problem:** Benchlab has no ground truth for review correctness. A reviewer that always approves would look good on cost but bad on quality.

**Fix:** Add `expected_review_decision` to scenario YAML. For scenarios with known bugs (like `failed_tests_repair` where the initial implementation has a bug), the expected decision is `reject`. For scenarios with correct implementations, expected is `approve`.

Report flags:
- **False approve:** reviewer approved but expected reject (quality miss)
- **False reject:** reviewer rejected but expected approve (cost waste from retries)

**Files:** `scenario.py` (add `expected_decision`), `report.py` (add quality metrics)  
**Acceptance:** `failed_tests_repair` scenario detects false approve if reviewer approves buggy code.

### 7.3 P2: 1-Month System Upgrades

#### P2-1: Claude session/continuation support

**Problem:** Every provider invocation is a fresh subprocess. Claude's prompt cache is per-conversation.

**Investigation needed:** Can Claude Code maintain a conversation across multiple `-p` calls? If yes:
- Planner output could be passed to implementer as conversation context
- Implementer output could be passed to reviewer as conversation context

Alternative: If Claude Code doesn't support this, use the Anthropic API directly with conversation history and explicit `cache_control` breakpoints. This would require a new `claude-api` provider (distinct from `claude-code`).

**Files:** New `providers/claude_api.py` (if API route), or `providers/claude_code.py` (if CLI supports continuation)  
**Impact:** Potential 80%+ cache hit rate within a task by reusing conversation context across phases.  
**Risk:** High implementation complexity. Claude Code may not support multi-turn via CLI.  
**Acceptance:** Three sequential provider calls within one task share cache (verified by token usage).  

#### P2-2: Prompt template versioning and registry

**Problem:** Prompt fragments (P1-2) need version tracking for A/B testing and rollback.

**Fix:** Add `prompt_version` to each fragment file (YAML front matter in `.txt` or separate `.meta.json`). Build a `PromptRegistry` in cc-loop that:
- Loads fragments by name + version
- Supports `--prompt-version` flag to pin a version set

**Files:** `src/cc_loop/prompts/` (add versioning), new `src/cc_loop/prompt_registry.py`

#### P2-3: Risk-triggered review depth

**Problem:** Reviewer is one-size-fits-all. No differentiation between trivial and critical changes.

**Fix:** Define risk signals:
- **Low risk:** ≤3 files changed, only docs/comments/tests, all tests pass
- **Medium risk:** 4-10 files, mixed source + test changes, all tests pass
- **High risk:** >10 files, security-sensitive paths (auth, crypto, permissions), test failures

Map to review depth:
- Low → fast review (artifact refs, approve if tests pass)
- Medium → standard review (current hybrid behavior)
- High → deep review (inline patches + explicit security check)

**Files:** `src/cc_loop/run.py` (risk classifier), `src/cc_loop/config.py` (review depth config)  
**Acceptance:** Three-line README change gets fast review; auth module change gets deep review.  

#### P2-4: Shared artifact schema library

**Problem:** Three projects parse cc-loop artifacts with duplicated, slightly different logic.

**Fix:** Extract `ccloop-artifacts` Python package:

```
    __init__.py
    models.py          # Unified dataclasses for ALL artifact types
    parsers.py         # from_path() for each artifact
    schemas.py         # JSON Schema definitions
```

All three projects depend on this package. cc-loop emits artifacts that conform. Benchlab and PromptOpsWorkbench parse using shared code.

**Files:** New repo `ccloop-artifacts`, update all three projects  
**Impact:** Eliminates duplication. Ensures schema consistency. Makes Luma integration reliable.  
**Risk:** Coordination across four repos.  
**Acceptance:** Benchlab and PromptOpsWorkbench import `ccloop_artifacts` and remove their own parsers.  

#### P2-5: Provider-side SLA and budget enforcement

**Problem:** Budgets exist (`max_wall_clock_seconds`, `max_consecutive_failures`) but aren't prominently surfaced. No per-phase budget.

**Files:** `src/cc_loop/budgets.py`, `src/cc_loop/config.py`, `src/cc_loop/inspect.py`

### 7.4 P3: Long-Term Product Direction

#### P3-1: Provider plugin system

**Problem:** Adding a new provider requires editing `providers/` directory and re-packaging cc-loop.

**Vision:** Providers are discovered from a directory (`~/.cc-loop/providers/` or `--providers-dir`). Each provider is a Python file or a JSON manifest + executable. This enables:
- Custom in-house providers
- Community-contributed providers
- Provider versioning independent of cc-loop

#### P3-2: PromptOpsWorkbench → cc-loop convergence

**Vision:** PromptOpsWorkbench becomes the **prompt management and analysis layer** for cc-loop:
- `promptops ccloop-import` imports cc-loop artifacts for editing
- `promptops cache` analyzes cache friendliness
- `promptops diff` compares prompt versions
- Edited prompts can be exported back as cc-loop fragment files (P1-2)

PromptOpsWorkbench does NOT run agents — it only manages prompts and analyzes artifacts.

#### P3-3: Luma as the unified workbench UI

**Vision:** Luma's Auto Workflow module becomes the primary UI for:
- Task creation (goal input, provider selection, test command)
- Live task monitoring (status, heartbeat, timeline)
- Task review (diff viewer, reviewer decision, merge control)
- Run history (past tasks, reports, cost tracking)
- Prompt inspection (imported from PromptOpsWorkbench)

Luma consumes cc-loop JSON output and PromptOpsWorkbench analysis JSON. It never runs agents directly.

#### P3-4: Luma Workbench integration

**Vision:** Luma's Workbench system (project identity, activity store, link store) integrates with cc-loop:
- "Continue with cc-loop" — capture current project context and spawn a cc-loop task
- "Review cc-loop changes" — open reviewer detail from any project
- Activity trail links to cc-loop task for each change

#### P3-5: Multi-provider benchmark leaderboard

**Vision:** cc-loop-benchlab maintains a public benchmark suite that ranks provider combinations on:
- Task success rate
- Token efficiency (cache hit rate, total tokens per task)
- Wall-clock speed
- Review accuracy (false approve/false reject rate)
- Cost per successful task

This drives provider selection and model choices.

## 11. Risks and Open Questions

### 11.1 Technical Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Reordering reviewer prompt breaks reviewer behavior | Medium | High | A/B test with benchlab before deploying |
| Two-stage reviewer lets bugs through (false approve) | Medium | High | Conservative escalation triggers; stage 1 is "fast" not "blind" |
| Claude session reuse not supported by Claude Code CLI | High | Medium | Fall back to API-based provider |
| Prompt fragment loading slows startup | Low | Low | In-memory cache after first load |
| Shared artifact schema breaks backward compatibility | Medium | Medium | Additive-only; version field in all schemas |
| Luma `resume` still broken after P0 fixes | Medium | Medium | Dedicated debugging session with Luma + cc-loop |

### 11.2 Product Risks

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| Four-project complexity becomes unmanageable | Medium | High | Shared artifact library (P2-4); clear boundaries |
| PromptOpsWorkbench scope creep | Medium | Medium | Define it as prompt management ONLY, not agent runtime |
| Benchlab becomes a product instead of a tool | Low | Medium | Keep it focused on cc-loop regression testing |
| Luma Auto Workflow grows beyond thin adapter | Medium | Medium | Enforce "Luma never imports cc-loop Python" rule |

### 11.3 Open Questions

1. **Can Claude Code CLI maintain conversation context across multiple `-p` calls?** This determines whether P2-1 is feasible or requires API-based provider.

2. **What is the actual cache behavior of Codex?** All cache analysis is Claude-centric. If Codex has different caching semantics, the optimization strategy changes.

3. **Does Cursor support prompt cache control?** Cursor implementer prompts are mostly dynamic. If Cursor doesn't cache, the implementer phase will always be a cache miss.

4. **Should cc-loop support non-Claude-family models?** The current architecture is Claude/Codex/Cursor-specific. GPT, Gemini, and open-source models would need different prompt engineering.

5. **Is the `chars/4` token heuristic accurate enough?** Real token counts from API responses show actual cache behavior. The heuristic is a proxy. Should cc-loop capture real token counts from provider output?

6. **Should benchlab become a GitHub Action or stay a CLI?** CI integration (P2-6) pushes toward GitHub Actions, but local execution is valuable for development.

## Appendix B: Prompt Cache Architecture (Current vs Proposed)

### Current
```
┌─────────────────────────────────────────────┐
│ Reviewer Prompt                              │
│                                              │
│ ┌─────────────────────────────────────┐     │
│ │ Stable Prefix (~16%)                │     │
│ │ - Review contract                    │     │
│ │ - Review rubric                      │     │
│ │ - JSON output contract               │     │
│ │ - Dynamic marker                     │     │
│ └─────────────────────────────────────┘     │
│ ┌─────────────────────────────────────┐     │
│ │ Dynamic Payload (~84%)              │     │
│ │ - Task metadata (goal, iteration...) │     │
│ │ - Node context (criteria, scope...)  │     │
│ │ - Review context (paths, refs...)    │     │
│ │ - Test result                        │     │
│ │ - Diff stat (INLINED!)              │     │
│ │ - Patches or refs                    │     │
│ └─────────────────────────────────────┘     │
│                                              │
│ Cache hit: ONLY the ~16% stable prefix       │
│ Cache miss: 84% of every reviewer call       │
└─────────────────────────────────────────────┘
```

### Proposed (P0-3)
```
┌─────────────────────────────────────────────┐
│ Reviewer Prompt                              │
│                                              │
│ ┌─────────────────────────────────────┐     │
│ │ Stable Contract (~15%)              │     │
│ │ - Review contract, rubric, JSON      │     │
│ └─────────────────────────────────────┘     │
│ ┌─────────────────────────────────────┐     │
│ │ Task Context (~25%)                 │     │
│ │ - Goal, node criteria, file scope    │     │
│ │ - Changes per TASK, not per attempt  │     │
│ └─────────────────────────────────────┘     │
│ ┌─────────────────────────────────────┐     │
│ │ Dynamic Payload (~60%)              │     │
│ │ - Attempt metadata (iteration...)    │     │
│ │ - Review context (refs only)         │     │
│ │ - Test result                        │     │
│ │ - Diff stat REF (not inlined!)      │     │
│ │ - Patch refs (not inlined!)          │     │
│ └─────────────────────────────────────┘     │
│                                              │
│ Cache hit: ~40% (stable + task context)      │
│ Cache miss: 60%                              │
│ Improvement: 2.5x cacheable content          │
└─────────────────────────────────────────────┘
```

### Proposed (P1-1, Two-Stage)
```
Stage 1: Fast Review
┌─────────────────────────────────────────────┐
│ Stable Contract (~60%)                      │
│ Dynamic: attempt metadata + refs (~40%)     │
│                                              │
│ Cache hit: ~60%                              │
│ Used for: 70-80% of reviews                  │
└─────────────────────────────────────────────┘

Stage 2: Deep Review (escalated only)
┌─────────────────────────────────────────────┐
│ Stable Contract + Task Context (~40%)       │
│ Dynamic: patches + evidence (~60%)          │
│                                              │
│ Cache hit: ~40%                              │
│ Used for: 20-30% of reviews                  │
└─────────────────────────────────────────────┘

Blended cache hit rate: 0.75*0.60 + 0.25*0.40 = ~55% stable prefix ratio
(versus current 16%)
```
